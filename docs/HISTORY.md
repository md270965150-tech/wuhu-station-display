## 1. 2026年5—6月：先明确场站怎么用

### 5月19—25日：上客区优化方案

早期讨论从真实动线、人车交织、乘客找车和现场秩序出发。方案涉及两排座椅、柱间可移动抽拉围栏、前部上车入口、两块车辆入/离场状态屏，以及合规订单识别道闸。围栏作为可调整的区域分控手段，不能为了形式固定不合理动线。

本阶段明确了“状态可视、候车导流、快进快出”的方向，不做车位级定位；远期地下负二层分区上车与西广场方案另行考虑。效果图要求保留现场原图与动线，采用16:9汇报画面。以上是场站方案与设计需求，不是B30某个软件版本已经落地全部硬件的证据。来源：S01。

### 6月26—30日：A/B上车语义与项目边界

导视标题逐步定为“芜湖站东广场负一层网约车A/B区上车指引”，强调车辆到达后按车牌对应分区上车。6月有离场信息未显示的反馈，指引地图和现场展板经历多次文字、位置与清晰度调整。

6月30日的讨论明确区分订单准入和A/B屏显，两者涉及不同供应商。订单接口规范、识别放行与本扩展的显示/播报不得混为同一交付。来源：S01。

### R8的关键意义

后续开发记录恢复了R8的有效源码与技术复盘。真正成功的链路是扩展/音频页 → 后台 → Chrome Native Messaging → Native Host → 本机Bridge → 上游自然语音，而不是浏览器直接WSS。

历史复盘记录的有效改动包括HTTP 101握手处理、真正的空子协议值、抑制无关异步返回值污染音频、完整字节数组返回，以及修正变量插值导致的车牌缺失。TLS校验保留；没有据此修改系统时间、关闭证书校验或认定代理是唯一根因。直接启动Host的新合成测试与之后的用户听音确认属于当时证据，不能代替未来每次Chrome运行验收。来源：S04。

### 稳定展示，再补齐B区语音
